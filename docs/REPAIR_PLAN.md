# REPAIR PLAN: DhanHQ Algorithmic Trading Platform (PAPER TRADING STATE)

The goal is to fix all architectural flaws discovered in the implementation audit and complete the system to a production-ready **PAPER TRADING** state. 

## Current Architecture & Audit Findings
- **Execution Loop:** Solid, but relies entirely on RAM (`PositionManager`). State is lost on restart.
- **Market Data:** Missing Dhan WebSockets; currently starved of real-time ticks.
- **Risk Management:** Good foundation, but missing broker-side SL protection.
- **AI Agents:** Currently mocked/stubbed placeholders returning strings.
- **Security:** FastAPI lacks authentication, allowing unauthorized access to dangerous endpoints.
- **Reconciliation:** No mechanism to sync local state with actual Dhan broker state.
- **Database:** SQLAlchemy models exist, but no repository layer integrates them into runtime.

## Proposed Implementation Phases (Migration Order)

### Phase 1: Persistence Layer & Alembic (Files: `backend/app/database/*`)
- Set up Alembic migrations.
- Expand `models.py` to include missing entities (`Trade`, `SystemEvent`, `AgentInsight`, `AuditLog`, `MarketSession`).
- Build Repositories (`OrderRepository`, `PositionRepository`, `SignalRepository`, etc.) to interface cleanly with SQLAlchemy.

### Phase 2: Runtime State Persistence (Files: `backend/app/execution/engine.py`, `worker/trading_worker.py`)
- Wire the `ExecutionEngine` to use the Repositories.
- Every state transition (Order Submitted, Filled, Cancelled) must be durably written to PostgreSQL immediately.

### Phase 3: Dhan WebSocket & Market Safety (Files: `backend/app/dhan/adapter.py`, `backend/app/market/validator.py`)
- Implement `asyncio`-based Dhan WebSocket client inside `DhanAdapter`.
- Implement `MarketDataManager` to handle missing ticks, duplicate ticks, and stale data timeouts (enforcing `SAFE_MODE`).
- Feed validated WebSocket ticks directly into `TradingWorker` and `CandleEngine`.

### Phase 4: Strategy Regression & Instrument Master (Files: `tests/regression/*`, `backend/app/market/instrument.py`)
- Create an `InstrumentManager` to fetch and parse Dhan's `api-scrip-master.csv` dynamically.
- Write a strict regression test comparing signals generated by `My Strategy/Option_RSI_strat.py` against the new `OptionRSIStrategy`.

### Phase 5: Broker Reconciliation & Idempotency (Files: `backend/app/execution/reconciliation.py`)
- Build a robust reconciliation engine comparing Dhan APIs (`get_positions`, `get_orders`) with the local DB.
- Handle state mismatches securely (e.g., entering `SAFE_MODE`).
- Implement Idempotency keys on all order requests to prevent duplicate broker executions.

### Phase 6: Stop-Loss Protection & Restart Recovery (Files: `backend/app/execution/engine.py`, `backend/app/worker/trading_worker.py`)
- Add broker-side Stop-Loss Market (SL-M) orders immediately upon position entry.
- Implement restart recovery in `main.py`: Re-authenticate, download broker state, reconcile, and reconstruct in-memory state from PostgreSQL before accepting new signals.

### Phase 7: API Security & Persistent Kill Switch (Files: `backend/app/api/auth.py`, `backend/app/risk/manager.py`)
- Add JWT middleware to secure `/start`, `/kill`, and other dangerous endpoints with an `ADMIN` role.
- Back the `KillSwitch` singleton with a PostgreSQL table so it persists across container restarts.

### Phase 8: Real AI Agents (Files: `backend/app/agents/*`)
- Implement a read-only `AIContextService`.
- Implement `TradingAnalystAgent`, `ReliabilityAgent`, and `PostMarketAnalyst` using the `google-genai` SDK and structured output schemas.
- Ensure strict read-only constraints in system prompts. Limit AI invocations to avoid excessive API costs.

### Phase 9: End-to-End Testing & Docker Validation
- Fix all outdated unit tests.
- Execute full Paper E2E tests simulating disconnects, stale data, and process crashes.
- Verify the full Docker compose stack (Postgres, Redis, Backend, Frontend).
